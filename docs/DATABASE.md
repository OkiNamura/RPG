# База данных Omika: разбор и план

Дата: 2026-11-04. Это не «надо всё переписать», а разбор того, где SQLite
реально ускорит Omika, а где JSON остаётся лучшим выбором.

## 1. Что есть сейчас

Текущий источник истины — один JSON на кампанию:

| Файл | Размер | Ходов | Лог | Снимки |
|---|---:|---:|---:|---:|
| `test-modern-child.json` | 4 067 КБ | 190 | 380 | 24 |
| `история.json` | 2 685 КБ | 98 | 196 | 24 |
| итого | 6,7 МБ | | 576 | 48 |

Внутри кампании:

- `state` — 222 / 134 КБ: герой, NPC, пати, предметы, локации, репутация;
- `turns` — 1 839 / 1 159 КБ: снимки последних ходов;
- `summary` — 41 / 21 КБ;
- `text` — ядро/мир/тон/герой;
- `agents` — промты и настройки;
- `meta` — настройки игры.

Отдельно:

- `data/traces/*.jsonl` — **147 МБ** за несколько дней;
- `data/vectors` — JSON-векторы;
- `data/inspectors`, `branches`, `cards`, `images`.

Запись сейчас атомарная: temp + rename всего JSON-файла. Для одной кампании
на 4 МБ это нормально, для десяти — уже неприятно.

## 2. Что даст база данных

### Реально даст

- **Поиск по логу** через FTS5: быстрее, чем перебирать массивы в JS.
- **Индекс персонажей/локаций/предметов**: навигация без чтения 4 МБ JSON.
- **Аналитику**: ходы, стоимость, модели, токены, изображения.
- **Хранение векторов** рядом с текстом: retrieval без чтения всех JSON.
- **Инкрементальную запись**: одна транзакция вместо перезаписи всего файла.
- **Трассы**: 147 МБ JSONL превращаются в таблицу с индексами.
- **Атомарность**: состояние, лог и снимок хода меняются вместе.

### Не даст

- «Умнее ИИ» само по себе. Качество поиска зависит от чанкинга, эмбеддингов,
  FTS-токенизации и запроса, а не от факта наличия SQLite.
- Бесплатной миграции. Нужны схема, синхронизация, бэкапы, миграции версий.
- Мгновенной скорости, если оставить гигантский JSON и просто положить его
  в BLOB: читать/писать его всё равно придётся целиком.

## 3. Замер прототипа

Собрал одноразовый SQLite-индекс поверх двух кампаний:

- 2 кампании, 576 записей лога;
- сборка: **~100 мс**;
- размер индекса: **~1,6 МБ** вместо 6,7 МБ кампаний;
- 200 FTS-запросов: **~4 мс** (на прогретом индексе);
- SQLite через `node:sqlite`, без внешних зависимостей.

Важная деталь: FTS5 точное слово `рынок` не находит `рынке/рынка`.
Для русского нужен prefix/stem-поиск: `рын*`, `пор*`. Прототип это уже делает.
Это не «баг БД», а обязательная настройка поиска.

Скрипт-прототип: `scripts/build-index.mjs`.

```powershell
node scripts/build-index.mjs
node scripts/build-index.mjs --query "рынок"
```

## 4. Три варианта

### A. Оставить только JSON

Плюсы: просто, переносимо, легко бэкапить, нет схемы.
Минусы: чтение всего файла для списка/поиска, перезапись 4 МБ за ход,
снимки раздувают кампанию, трассы не индексируются.

Для текущих 2 кампаний это всё ещё рабочий вариант.

### B. Полностью перевести state на SQLite

Нормализовать героя, NPC, пати, предметы, локации, лог, снимки, валюты.
Плюсы: быстрые запросы, транзакции, масштабирование.
Минусы: большая миграция, риск потерять данные, много кода на все вложенные
структуры, сложнее бэкап и отладка. Для пилота это преждевременно.

### C. Гибрид: JSON — истина, SQLite — индекс/кэш

JSON остаётся каноническим и восстанавливаемым. SQLite хранит:

- метаданные кампаний;
- персонажей/локации/предметы;
- лог и FTS;
- снимки/векторы/трассы (поэтапно);
- поиск и агрегаты.

Плюсы: быстрый поиск уже сейчас, низкий риск, индекс можно удалить и
пересобрать. Минусы: нужна синхронизация, но она проще полной миграции.

**Рекомендация: C, поэтапно.**

## 5. Целевая схема

```sql
campaigns(
  id TEXT PRIMARY KEY,
  title TEXT,
  preset TEXT,
  turn INTEGER,
  place TEXT,
  saved_at TEXT,
  size INTEGER,
  cost REAL
);

actors(
  campaign_id TEXT, name TEXT, kind TEXT, status TEXT,
  role TEXT, attitude INTEGER, morale INTEGER, present INTEGER,
  PRIMARY KEY(campaign_id, kind, name)
);

locations(campaign_id, name, note, description, history, card);
items(campaign_id, name, qty, place, card);
log(campaign_id, turn, role, text);
log_fts USING fts5(campaign_id, text, turn, role);

summaries(campaign_id, text);
snapshots(campaign_id, turn, json);
vectors(campaign_id, turn, text, model, vector BLOB);
traces(id, ts, campaign_id, turn, model, tokens_in, tokens_out, cost, prompt, prose);
images(campaign_id, kind, name, url, created_at);
```

`state` пока не разбиваем на десятки таблиц: его можно хранить как JSONB/JSON,
а отдельные таблицы держать только для поиска.

## 6. Синхронизация

### Фаза 1 — индекс для чтения (уже сделано)

- `scripts/build-index.mjs` собирает `data/search.db`.
- Индекс одноразовый, пересобирается из JSON.
- `/api/search?q=` и страница «Поиск» (`Ctrl+K`) добавлены.
- Индекс не влияет на ход игры.

### Фаза 2 — инкрементальная запись

- После `persist` обновлять строки кампании, лог, персонажей, локации.
- Новые строки лога — append; снимки — upsert.
- Всё в одной транзакции.
- Если БД упала/отстала — пересборка, игра не ломается.

### Фаза 3 — тяжёлые данные

- Снимки (`turns`) — в `snapshots`; JSON кампании уменьшается в 5–6 раз.
- Трассы — в `traces`; поиск и статистика.
- Векторы — в `vectors`; JSON-векторы остаются экспортом.
- Ветки — в `branches`/`snapshots`.

### Фаза 4 — только если появится мультипользовательность

- Нормализованный state, миграции, конкурентный доступ.

## 7. Что проверить перед внедрением

1. `node:sqlite` в текущей Node 24.21: API `DatabaseSync` есть.
2. WAL и `busy_timeout`; один процесс-писатель.
3. FTS5-токенизация русского; prefix/stem обязателен.
4. Бэкап: JSON + `VACUUM INTO`.
5. Бенчмарк на 10+ кампаниях и 1 ГБ трасс.
6. Тест «битая БД»: приложение работает на JSON, индекс пересобирается.
7. Не хранить в БД секреты/ключи.

## 8. Что делать сейчас

Не спешить с полной миграцией. Сделать **фазу 1**:

- собрать `data/search.db` скриптом;
- добавить `/api/search` и простую палитру;
- использовать FTS/векторы для retrieval, не меняя turn-state;
- замерить на реальных 50+ ходах.

Если после этого поиск/навигация станут заметно лучше — двигать снимки и
трассы в SQLite. Полную нормализацию state делать только при реальной
мультипользовательности.
