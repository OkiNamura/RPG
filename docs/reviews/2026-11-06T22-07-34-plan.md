# plan: Очередь B: память rev3

ВЕРДИКТ: ОК

Блокеры: нет.

Проверил по коду три пункта, которые раньше были блокерами или рисками, — все закрыты:
- **Кэш контекста.** `memory.recall` стоит после `lore.after` и до `state`: `context.ts:353-362`. Закреплённые записи идут в слот `memory` (`context.ts:298`) в стабильном порядке.
- **Undo и regenerate.** Записи лежат в сессии, поэтому `restoreTo` (`server.ts:2020`, вызовы в `:3655` и `:3697`) их не трогает.
- **Гонка с ходом.** `busy` выставляют и turn, и stream (`server.ts:4924-4925`), regenerate (`:3659`) и edit (`:3701`). Проверка 409 в плане работает.

Риски:
1. **Recall-ключи сравниваются простым вхождением подстроки.** Это и есть второй матчер, хотя план пишет «без второго матчера». Сопоставление по ключам уже есть: `hitsKey` в `src/core/lore.ts:38-45`. Там есть грубый стемминг, но функция не экспортирована. Без стемминга ключ «кольцо» не найдёт «кольца» и «кольцом». Как проверить: тест «ключ `кольцо`, ввод `беру кольца`», запись должна попасть. Предлагаю экспортировать `hitsKey` и использовать его.
2. **Бюджет 9k не сходится с лимитами.** Блоки дают 4000 (старая строка) + 4000 (закреплённые) + 3000 (recall) = 11000. В плане не сказано, кто уступает. Нужно явно: recall получает остаток, `min(3000, 9000 − legacy − pinned)`. При полной строке и полном закреплённом блоке на recall остаётся 1000. Тест: строка 4000 + закреплённые 4000 + recall 3000 → весь блок памяти ≤ 9000, в отчёт инспектора попадают вытесненные записи recall.
3. **`update` может обойти лимит закреплённого блока.** План проверяет 4000 символов только при `pin`. Если игрок закрепил 7 записей по ~550 символов (всего 3850), а потом через `update` удлинил одну до 500 при лимите 4000, должен быть ответ 400. Тест: update текста закреплённой записи сверх лимита → 400.
4. **Нет способа загрузить список при открытии модалки.** Записи приходят только в ответе на POST. GET кампании (`server.ts:3612-3623`) и container (`:3605`) отдают только `memory`. После перезагрузки страницы модалка будет пустой. Нужно добавить `memories` в GET кампании.
5. **Роут.** `memory-entry` нужно добавить в regex `campaignMatch` (`server.ts:3449`), иначе ответ 404. Сейчас там только `memory`.
6. **Где считается recall, не сказано.** Его нужно считать в `prepareTurn` (`server.ts:1501`), рядом с `pickLore`. Тогда turn, stream, regenerate и edit получат одинаковый набор (единый pipeline A5). Если считать в одной точке входа, regenerate и edit разойдутся с обычным ходом.
7. **Состав сегмента `memory` не определён.** Неясно, будут ли старая строка и закреплённые записи одним сегментом `memory` или двумя. Если двумя, нужны два разных имени и фиксированный порядок между ними. Иначе инспектор и `cachedPrefix` будут сравнивать не те сегменты.
8. **Отчёт инспектора.** `lastMemoryReport` нужно добавить в JSON внутри `persist` (`server.ts:1961-1968`), рядом с `lore:`. Для этого в плане нет теста «инспектор после рестарта показывает отчёт recall».
9. **Тест стабильности слишком узкий.** «Сегменты до `conspect` стабильны» мало: recall стоит после `lore.after`. При одинаковом лоре и разном recall совпадать должны хэши всех сегментов до `lore.after` включительно.
10. **Валидация API не описана целиком.** Не задан диапазон `importance` (1..3?), не сказано, что делать с неизвестным `kind` (400 или подставить значение по умолчанию), нет обрезки и дедупликации ключей и проверки `id` на update, delete и pin (неизвестный id → 404).
11. **PWA.** Нужно поднять версию `omika-shell-v54` в `sw.js:3`. В CONTEXT.md, раздел UI, модалки закрываются ещё свайпом вниз и системным «Назад». В плане перечислены только Esc, фон и фокус-трап, а нужны все пять способов.

Не согласен:
