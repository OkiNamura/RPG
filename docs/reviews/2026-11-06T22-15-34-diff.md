**Блокеры:**
1. `src/server.ts:3926-3927`: «Закрепить» и «Открепить» сбрасывают важность записи на 2, а тип — на `journal`. Для этих действий UI отправляет только `{action, id}` (`app.js:5844`). Сервер берёт `kind` и `importance` из тела запроса и не подставляет значения из существующей записи, хотя для `text` и `keys` это сделано. Пример: игрок добавил запись с важностью «высокая» (3), нажал «Закрепить» — в сохранённой записи уже 2. От важности зависит порядок и обрезка закреплённых записей (`memory.ts:51-52`), а также приоритет recall (`memory.ts:72`). Пользователь этого не увидит: важность в UI не показывается. То же происходит при `update` без `kind`/`importance` и при неизвестном `action` с существующим `id`: такой запрос тоже обрабатывается как update.
   - Исправить: `body.kind ?? entry?.kind`, `body.importance ?? entry?.importance`; неизвестный `action` → 400.
   - Проверить: тест через API. Добавить запись с `importance: 3`, сделать `pin`, затем GET кампании — должно быть `importance === 3`.

**Риски:**
1. Сервер и сборщик блока по-разному считают лимит закреплённых записей. API проверяет сумму `text.length ≤ 4000` (`server.ts:3951`). `buildMemoryBlock` считает `"- " + text` плюс перевод строки (`memory.ts:57-61`). Если закрепить 8 записей по 500 символов, API их примет, а 8-я молча не попадёт в контекст: её нет и в `dropped`. Нужно либо считать одинаково, либо ставить лимит текста с запасом.
2. У кнопок «Закрепить», «Открепить» и «Удалить» нет `try/catch` (`app.js:5841-5856`). Ответы 400 «переполнена», 409 «ход идёт» и 404 станут необработанным rejection, и пользователь ничего не увидит. У «Добавить» обработка ошибки есть.
3. В `style.css` нет стилей `.memory-entry`, `.memory-entry-text`, `.memory-entry-meta` и `.memory-form`. Строка списка — это четыре inline-элемента подряд, на мобильном они будут слипаться. Нужно проверить скриншотом на ширине 375.
4. Ветки (`server.ts:3421-3432`, `3441-3445`) сохраняют и восстанавливают старое поле `memory`, но не `memories`. Если записи принадлежат кампании, это осознанно. Но поведение двух видов памяти при загрузке ветки расходится, и это нигде не записано. Нужно решение пользователя или запись в CONTEXT.md.
5. `restart` (`server.ts:4255`) без подтверждения удаляет `memories` — записи, которые «переживают откаты». Это согласовано с очисткой `memory`, но удаление данных необратимое. Проверить, что UI restart предупреждает именно об этом.
6. `lastMemoryReport` пишется в инспектор (`server.ts:1971`, `3561`), но в `app.js` его никто не читает: ни `usedRecall`, ни `dropped` в UI не выводятся. Вытесненные recall-записи не видны.
7. `normalizeMemories`:
   - не дедуплицирует `id`;
   - если `createdTurn` не число, будет `NaN`, и сортировка в `memory.ts:51,72` станет нестабильной.

   Для старых и ручных сейвов это маловероятно, но дёшево закрыть.
8. Recall считается в `runTurn` (`turn.ts:222`), а не в `prepareTurn`. Пути turn, stream, regenerate и edit всё равно проходят через `runTurn`, так что набор у них одинаковый. Но это расходится с рекомендацией 6 из ревью плана, и при повторном вызове ведущего recall пересчитывается.
